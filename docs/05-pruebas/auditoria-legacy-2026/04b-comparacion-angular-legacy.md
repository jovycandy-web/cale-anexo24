# 04b — Comparación de requisitos de ventanas legacy (RF-057..RF-098) contra la implementación Angular + Spring Boot

- **Alcance:** trazabilidad funcional de los requisitos **RF-057 a RF-098** de `03-matriz-requisitos.md` (sección *Requisitos de ventanas legacy*, derivados de las fichas SCR-022…SCR-062) contra el código del repositorio del proyecto (Angular 22 en `frontend/src`, Spring Boot 4.1 en `backend/src/main/java`, procedimientos en `infra/sql`).
- **Modo:** solo lectura. No se modificó ningún archivo del repositorio. No se ejecutó Git ni la aplicación.
- **Fecha de consolidación:** 2026-10-21.
- **Continuidad:** documento complementario de `04-comparacion-angular.md` (RF-001..RF-056). Mismas reglas de clasificación y convención de evidencia.
- **Método:** para cada RF se buscó el equivalente en rutas, componentes, servicios, controladores, adaptadores JDBC y procedimientos almacenados; se clasificó según la evidencia encontrada y se registró `archivo:línea`. Cuando la ausencia de una capacidad se afirma, se documenta la búsqueda negativa (grep sin coincidencias sobre `backend/src/main/java`, `infra/sql/procedures/**` y `frontend/src`).
- **Regla de clasificación:**
  - **CUMPLE** — la funcionalidad existe con evidencia directa y satisface el enunciado.
  - **PARCIAL** — existe la funcionalidad base pero falta o diverge una parte verificable del enunciado (columnas, permisos, formato, fase, granularidad de filtro, obligatoriedad).
  - **NO CUMPLE** — no existe implementación de lo exigido (o existe y contradice el enunciado).
  - **NO VERIFICABLE** — no hay evidencia en el repositorio que permita emitir un juicio en uno u otro sentido.
- **Convención de evidencia:** `ruta/relativa/archivo.ext:línea` (o `:línea-línea`). Rutas relativas a la raíz del repositorio. `frontend/...` = `frontend/src/app/...` cuando el archivo está bajo `app`.

## 5. Notas de método y límites

- **Sin evidencia = NO VERIFICABLE.** Ninguno de los 42 RF quedó en NO VERIFICABLE: en todos los casos se localizó implementación, se documentó la ausencia por búsqueda negativa reproducible, o se citó un documento de mapeo versionado que declara el estado del contrato legacy.
- **Cláusulas dependent de datos vivos.** Los conteos del legacy (1128 materiales, 2632 productos, 5039 estructuras, 27/73/43 columnas ya reflejadas en contratos de SP) no son verificables desde el repositorio; dependen del contenido de `CALE_IMMEX`. La clasificación refleja la **implementación observable**, no el volumen de datos.
- **Convención de counting.** Un RF se clasificó como PARCIAL cuando existe la superficie funcional y falla un sub-requisito verificable (número de columnas, obligatoriedad, permiso, fase, granularidad de filtro). Un RF se clasificó como NO CUMPLE cuando la capacidad no existe o el contrato implementado contradice explícitamente el enunciado (p. ej. 7 columnas donde se exigen 31 con banderas de unidad).
- **Substituciones aceptadas como cumplimiento.** RF-097 se clasificó CUMPLE por sustitución arquitectónica: no hay superficie ASPX que restringir, y el control equivalente (autenticación + `@PreAuthorize` en servidor + guard de ruta con `/forbidden`) está implementado. RF-059, RF-060, RF-061 y RF-065 son Catálogos auxiliares read-only agrupados en una sola superficie (`/catalogos`), no ventanas 1:1, pero el contenido del requisito está íntegramente presente.
- **Documentación citada como contexto, no como prueba primaria.** Los archivos bajo `docs/03-diseno/` y `docs/05-pruebas/` se usan para confirmar el *estado del contrato legacy* cuando el repositorio no contiene la definición original (p. ej. `PR_INFORME_SALDOS`, `dbo.CargaMaterial`, `dbo.CargaPedimentosIE`); la evidencia primaria de cada fila es el archivo de código o procedimiento citado.
- **Sin ejecución.** No se compiló, no se ejecutaron pruebas y no se levantó la aplicación; toda conclusión es estática sobre el código versionado.
